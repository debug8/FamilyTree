# Family Tree — Специфікація та план розробки

Настільний застосунок на **C# / WPF** для збереження, редагування та візуалізації фамільного (генеалогічного) дерева з автоматичним визначенням ступеня родинного зв'язку між будь-якими двома особами.

Документ структуровано так, щоб кожен розділ і кожну задачу можна було передавати LLM як самостійне технічне завдання. Задачі пронумеровані (T-x.y), мають чіткі вхідні умови, результат і критерії приймання.

---

## 1. Загальний опис і цілі

### 1.1. Призначення
Користувач веде базу осіб своєї родини: додає людей, вказує родинні зв'язки (батько/мати — дитина, подружжя), а застосунок:
- будує графічне дерево **вгору** (предки) або **вниз** (нащадки) від обраної особи;
- показує **всіх** родичів обраної особи — прямих і непрямих (бічні гілки: брати/сестри, дядьки, племінники, двоюрідні тощо);
- для кожної відображеної особи підписує **назву родинного зв'язку** відносно кореневої особи (наприклад: «тітка», «племінник», «двоюрідна тітка», «троюрідний брат», «прабаба»).

### 1.2. Ключові сценарії використання (Use Cases)
| ID | Сценарій |
|----|----------|
| UC-1 | Додати нову особу з персональними даними |
| UC-2 | Редагувати / видалити особу |
| UC-3 | Додати зв'язок «батько/мати → дитина» |
| UC-4 | Додати зв'язок «подружжя» |
| UC-5 | Обрати кореневу особу та побудувати дерево предків (вгору) |
| UC-6 | Побудувати дерево нащадків (вниз) |
| UC-7 | Побудувати повне дерево родичів (предки + нащадки + бічні гілки) |
| UC-8 | Побачити назву родинного зв'язку кожної особи відносно кореневої |
| UC-9 | Запитати ступінь родства між двома довільними особами |
| UC-10 | Пошук особи за прізвищем/ім'ям |
| UC-11 | Зберегти родину у файл `.familytree`; відкрити існуючий файл |
| UC-12 | Злиття з іншим файлом родини; імпорт/експорт GEDCOM |
| UC-13 | Перемкнути мову інтерфейсу (українська / англійська) — включно з назвами родства |

### 1.3. Нефункціональні вимоги
- **Платформа:** Windows 10/11, .NET 10 (LTS), WPF. (.NET 10 — актуальний LTS, підтримка до листопада 2028; .NET 8/9 виходять з підтримки 10.11.2026, тому для нового проєкту обрано 10.)
- **Архітектура:** MVVM (рекомендовано `CommunityToolkit.Mvvm`).
- **Зберігання:** модель «документ»: одна родина = один файл `.familytree` (JSON усередині). Весь граф завантажується в пам'ять; збереження — атомарний перезапис файлу. Без СУБД (обґрунтування — розділ 3.5). Доступ до сховища — тільки через інтерфейс `IFamilyStorage`, щоб за потреби замінити реалізацію на SQLite без змін у домені та UI.
- **Продуктивність:** коректна робота з файлом до ~5 000 осіб; побудова дерева до 8–10 поколінь без помітних затримок (< 1 c); збереження файлу < 200 мс.
- **Локалізація:** застосунок мультимовний від початку. Мова за замовчуванням — українська, друга мова — англійська (як доказ працездатності механізму). Жодного рядка, видимого користувачу, в коді чи XAML напряму; назви родства — через `IKinshipFormatter` окремо для кожної мови; перемикання мови — з налаштувань без перезапуску (або з м'яким перезапуском вікна). Деталі — розділ 2.4.
- **Тестованість:** доменна логіка (модель, алгоритм родства) — в окремому проєкті без залежності від WPF; покриття unit-тестами (xUnit + Shouldly; моки — NSubstitute, лише для ViewModel-ів).

## 2. Архітектура рішення

### 2.1. Структура solution
```
FamilyTree.sln
├── FamilyTree.Domain        // Сутності, доменні сервіси, алгоритм родства. Без залежностей від UI.
├── FamilyTree.Storage       // IFamilyStorage + JsonFamilyStorage: серіалізація, атомарний запис, бекапи.
├── FamilyTree.Gedcom        // Обмін GEDCOM 5.5.1: читач/писач, мапінг INDI/FAM ↔ модель (T-5.2). Залежить від Domain і Storage.
├── FamilyTree.App           // WPF: Views, ViewModels, конвертери, стилі, ресурси локалізації, DI-контейнер.
└── FamilyTree.Tests         // xUnit + Shouldly (+ NSubstitute для ViewModel-ів): домен, сховище, локалізація.
```

### 2.2. Принципи
- **MVVM:** View (XAML) ↔ ViewModel (команди, стан) ↔ Domain/Storage. Code-behind — тільки для суто візуальних речей (zoom/pan на Canvas).
- **DI:** `Microsoft.Extensions.DependencyInjection` + `Microsoft.Extensions.Hosting`; реєстрація `IFamilyStorage`, доменних сервісів, `ILocalizationService`, ViewModel-ів.
- **Документна модель:** відкритий файл живе в пам'яті як `FamilyDocument` (особи + зв'язки + метадані); ViewModel-и працюють з ним напряму, `IFamilyStorage` викликається лише на Open/Save. Прапорець «є незбережені зміни» (*) у заголовку вікна.
- **Асинхронність:** читання/запис файлу — `async`; UI не блокується.
- **Валідація:** на рівні домену (інваріанти) + на рівні ViewModel (`INotifyDataErrorInfo`).

### 2.3. Основні компоненти
| Компонент | Шар | Відповідальність |
|-----------|-----|------------------|
| `Person`, `ParentChildLink`, `SpouseLink` | Domain | Сутності |
| `FamilyGraph` | Domain | Побудова графа в пам'яті з сутностей; навігація (батьки, діти, подружжя, сиблінги) |

| `GedcomReader`, `GedcomImporter`, `GedcomExporter`, `GedcomFamilyBuilder` | Gedcom | Читання/запис `.ged`; виведення `FAM` з ребер і назад; звіт про імпорт (T-5.2) |

### 2.4. Механізм локалізації
Три категорії текстів, у кожної — свій механізм:

1. **Статичні рядки UI** (написи, кнопки, заголовки, повідомлення валідації): `.resx`-ресурси в `FamilyTree.App/Resources` — `Strings.resx` (українська, базова) + `Strings.en.resx`. Доступ із XAML — через markup extension `{loc:Localize Key}` або статичний клас-обгортку; з коду — через `ILocalizationService.GetString(key)`. Ніяких literal-рядків у XAML/коді (перевіряється код-рев'ю; опційно — Roslyn-аналізатор).
2. **Назви родства** — це не переклад, а **окрема логіка для кожної мови** (англійська система інша: first cousin once removed ≠ буквальний переклад «двоюрідного дядька»). Тому: інтерфейс `IKinshipFormatter` у Domain; реалізації `UkrainianKinshipFormatter`, `EnglishKinshipFormatter`; вибір реалізації — за поточною культурою через DI-фабрику. Тести — окремо на кожен форматер.
3. **Формати дат і чисел** — через `CultureInfo` поточної мови (`DateOnly.ToString(culture)`), без ручного форматування.

Правила:
- Поточна мова зберігається в `settings.json`; при старті виставляється `Thread.CurrentThread.CurrentUICulture`.
- Перемикання мови в налаштуваннях: **зафіксовано (T-0.2) — живе оновлення без перезапуску**. Markup extension `{loc:Localize Key}` повертає прив'язку до індексатора класу-проксі `LocalizationSource` (реалізує `INotifyPropertyChanged`); `ILocalizationService.SetLanguage` піднімає подію `LanguageChanged`, за якою проксі сигналить оновлення індексатора (`Binding.IndexerName`) — і всі написи перечитуються миттєво. Дати/числа оновлюються через прив'язки до властивостей ViewModel, що реагують на `LanguageChanged`.
- Ключі ресурсів — ієрархічні: `Person_Editor_Title`, `Validation_CycleDetected`, `Tree_Mode_Ancestors`.
- Ідентифікація мови — за **власним кодом** застосунку (`LanguageOption.Code`), а не за `CultureInfo.TwoLetterISOLanguageName` (той не унікальний і для рідкісних мов повертає трилітерний код). Форматування дат/чисел — за окремим `FormattingCulture`, який має відкат, якщо реальної `CultureInfo` немає. Невідомий/битий код мови в `settings.json` не викидає виняток — тихий відкат на мову за замовчуванням.
- Додавання нової мови — два шляхи: (а) **вбудована** (є `CultureInfo`): новий `Strings.xx.resx` + `RegisterBuiltIn("xx")` + новий `XxKinshipFormatter`; (б) **без `CultureInfo`** (діалект/штучна/рідкісна мова): файл перекладу `%AppData%\FamilyTree\languages\<code>.json` (`displayName`, необов'язковий `formattingCulture`, `strings`), який підхоплюється при старті; відсутні ключі беруться з нейтральної мови. Деталі — `docs/localization-custom-languages.md`. Жодних змін у логіці.

## 3. Модель даних

### 3.1. Сутність `Person`
| Поле | Тип | Обов'язк. | Примітка |
|------|-----|-----------|----------|
| `Id` | Guid | так | PK |
| `LastName` | string(100) | так | Прізвище |
| `FirstName` | string(100) | так | Ім'я |
| `MiddleName` | string(100) | ні | По батькові |
| `MaidenName` | string(100) | ні | Дівоче прізвище |
| `Gender` | enum `Gender { Male, Female, Unknown }` | так | Потрібен для назв родства (дядько/тітка) |
| `BirthDate` | FamilyDate? | ні | Може бути невідома. З формату v2 — `FamilyDate` (точна/часткова/приблизна/діапазон/фраза), див. T-5.2a |
| `BirthPlace` | string(200) | ні | |
| `DeathDate` | FamilyDate? | ні | Див. T-5.2a. `null` — дата невідома АБО особа жива; розрізняє `Deceased` |
| `Deceased` | bool | ні | Явна позначка «помер», коли дата невідома (GEDCOM `1 DEAT` без `DATE`). Прапорець позитивний навмисне: `false` за замовчуванням = «живий», тож старі файли без поля читаються правильно. Та сама конструкція, що й `SpouseLink.Divorced`. `false` у файл не пишеться |
| `IsAlive` | bool (обчислюване) | — | `DeathDate == null && !Deceased` |
| `PhotoPath` | string? | ні | Копія фото в папці даних застосунку |
| `Notes` | string? | ні | Довільні нотатки |
| `Facts` | List\<PersonFact\> | ні | Життєві факти: професія, проживання. Порядок значущий — його задає джерело. Порожній список у файл не пишеться |
| `CreatedAt` / `UpdatedAt` | DateTime | так | Аудит |

**`PersonFact`** — життєвий факт особи. `record` без власного `Id`: поза особою він не живе,
а 36 символів Guid на запис у людиночитному файлі задорого. Наслідки — рівність за значенням
(два однакові факти не розрізняються) і зміна через `with`.

| Поле | Тип | Примітка |
|------|-----|----------|
| `Kind` | enum `PersonFactKind { Occupation, Residence, Other }` | Вид факту |
| `Label` | string? | Лише для `Other` — оригінальна назва виду з файлу новішої збірки |
| `Value` | string? | Суть: професія. Для проживання зазвичай порожнє — усе значення несе `Place` |
| `Date` | FamilyDate? | Коли; підтримує неточні дати й періоди (T-5.2a) |
| `Place` | string? | Де |

`Other` — не «різне», а запобіжник сумісності: файл із видом, якого ця збірка не знає, має
читатися без втрат і без падіння. Тому вид у JSON — **рядок**, а не enum через
`JsonStringEnumConverter`: конвертер кинув би `JsonException`, і користувач побачив би
«файл пошкоджено» через один незнайомий запис. Невідомий рядок читається як `Other` зі
збереженням оригіналу в `Label` і повертається у файл незміненим. Той самий підхід, що й
у `FamilyDateDto.Kind`. Схема лишається **v2**: поле опційне, старий файл без `facts`
читається як порожній список.

### 3.2. Зв'язки
**`ParentChildLink`** — спрямоване ребро «батько/мати → дитина»:
| Поле | Тип | Примітка |
|------|-----|----------|
| `Id` | Guid | PK |
| `ParentId` | Guid | FK → Person |
| `ChildId` | Guid | FK → Person |
| `ParentRole` | enum `ParentRole { Biological, Adoptive, Step }` | На старті достатньо `Biological`; enum закладаємо одразу |

**`SpouseLink`** — ненапрямлене ребро «подружжя»:
| Поле | Тип | Примітка |
|------|-----|----------|
| `Id` | Guid | PK |
| `Person1Id` / `Person2Id` | Guid | FK → Person; зберігати з `Person1Id < Person2Id` для унікальності |
| `MarriageDate` | FamilyDate? | З формату v2 — `FamilyDate` (див. T-5.2a) |
| `DivorceDate` | FamilyDate? | `null` = дата невідома **або** шлюб чинний (див. `IsActive`); тип — `FamilyDate` з v2 (T-5.2a) |
| `Divorced` | bool | Шлюб завершено, коли дату розлучення не вказано (у діалозі знято «В шлюбі»). Опційне поле формату: відсутнє/`false` для старих файлів |

Чинність шлюбу — обчислюване: `IsActive = DivorceDate is null && !Divorced`. Поле `Divorced` додано, щоб
стан «не в шлюбі, дата невідома» зберігався окремо (інакше `DivorceDate = null` завжди означав би чинний шлюб).

### 3.3. Інваріанти та валідація (доменні правила)
1. У особи не більше **одного біологічного батька** та **однієї біологічної матері** (перевірка за `Gender` батьків + `ParentRole = Biological`).
2. Заборона **циклів**: особа не може бути власним предком (перевірка DFS-ом по predkam при додаванні `ParentChildLink`).
3. Заборона дубля ребра: той самий `ParentId`+`ChildId`. Для `SpouseLink` дублем є та сама пара з **перетином періодів** шлюбу — **повторний шлюб** тієї самої пари з роздільними періодами (розлучились → одружились знову) дозволено й зберігається окремим записом.
4. Особа не може бути в шлюбі сама з собою; не може бути батьком самої себе.
5. М'які попередження (не блокують збереження, але показуються): дитина народжена до 12-річчя батька/матері; дата смерті раніша за дату народження; батько/мати молодші за дитину.

### 3.4. ER-діаграма (текстово)
```
Person 1 ──< ParentChildLink >── 1 Person   (Parent → Child)
Person 1 ──< SpouseLink >── 1 Person        (симетричний зв'язок)
```

### 3.5. Формат зберігання: файл `.familytree` (JSON)
СУБД не використовується. Обґрунтування: застосунок все одно тримає весь граф у пам'яті (алгоритм родства та розкладка дерева працюють з повним `FamilyGraph`), обсяг даних малий (5 000 осіб ≈ 2–3 МБ), а модель «родина = документ» природна для користувача: файл можна копіювати, синхронізувати через хмару, надсилати родичам.

**Структура файлу:**
```json
{
  "schemaVersion": 1,
  "meta": { "title": "Родина Шевченків", "createdAt": "...", "updatedAt": "...", "appVersion": "0.9.3" },
  "persons": [ { "id": "...", "lastName": "...", "firstName": "...", "gender": "Male", "birthDate": "1954-03-01", ... } ],
  "parentChildLinks": [ { "parentId": "...", "childId": "...", "parentRole": "Biological" } ],
  "spouseLinks": [ { "person1Id": "...", "person2Id": "...", "marriageDate": null, "divorceDate": null } ]
}
```

Примітки до полів: `meta.appVersion` — версія збірки, що **останньою зберегла** файл (проставляється автоматично зі
збірки; для файлів без цього поля — порожньо, авторство не вигадується). `spouseLinks` може містити опційне
`"divorced": true` — стан «шлюб завершено, дата невідома» (за замовчуванням `false` у файл не пишеться).
`parentRole` — опційний (`Biological` за замовчуванням; `Adoptive`/`Step` для нерідних зв'язків).

**Формат v2 (дати).** Починаючи зі `schemaVersion: 2`, поля дат (`birthDate`, `deathDate`, `marriageDate`,
`divorceDate`) серіалізуються не рядком ISO, а об'єктом `FamilyDate` (див. T-5.2a), напр.
`{"kind":"exact","y":1980,"m":3,"d":14}`, `{"kind":"approx","q":"about","y":1850}`,
`{"kind":"range","range":"between","from":{…},"to":{…}}`, `{"kind":"phrase","text":"…"}`; опційні `cal`
(лише `julian`) і `gedcom` (сирий GEDCOM-вираз для round-trip). Файли v1 (дата рядком ISO) читаються через
міграцію `IFormatMigration (v1→v2)`, яка перетворює їх на `kind:"exact"` — без утрат і без запису у звіт полагоджень.

**Обов'язкові правила надійності:**
1. **Атомарний запис:** серіалізація в тимчасовий файл поруч → `File.Replace` (або rename) поверх цільового. Падіння процесу під час збереження ніколи не псує наявний файл.
2. **Версія схеми:** поле `schemaVersion`; читання файлу з новішою версією — зрозуміла відмова; зі старішою — ланцюжок міграторів `IFormatMigration (v1→v2→…)`.
3. **Резервні копії:** перед перезаписом — копія в підпапку `.backups` поруч із файлом (тримати останні 5, ротація).
4. **Фото** зберігаються не в JSON, а в папці `<ім'я файлу>.media/` поруч; у JSON — відносні шляхи.
5. Серіалізація — `System.Text.Json` (camelCase, enum-и рядками, `WriteIndented = true` для дружності до diff/git).

## 4. Алгоритм визначення ступеня родства (ядро застосунку)

### 4.1. Постановка
Для двох осіб **A** (коренева, «я») та **B** треба визначити: *ким є B для A* — і повернути українську назву з урахуванням статі B.

### 4.2. Крок 1: пошук найближчого спільного предка (НСП)
1. BFS-ом вгору по ребрах «дитина → батьки» зібрати для A множину предків з відстанями: `ancA[person] = a` (сама A має відстань 0).
2. Те саме для B: `ancB[person] = b`.
3. Спільні предки = перетин множин. Обрати НСП з мінімальною сумою `a + b` (при рівності — з мінімальним `max(a,b)`).
4. Якщо спільного предка немає — перевірити зв'язок через шлюб (див. 4.5), інакше «родинний зв'язок не встановлено».

> Особливий випадок: якщо B ∈ ancA, то НСП = B (b = 0); якщо A ∈ ancB — НСП = A (a = 0).

### 4.3. Крок 2: класифікація за парою (a, b)
`a` — відстань від A до НСП, `b` — відстань від B до НСП.

| Умова | Хто B для A | Назви (чол. / жін.) |
|-------|-------------|---------------------|
| a=0, b=1 | дитина | син / дочка |
| a=0, b=2 | онук | онук / онука |
| a=0, b=3 | правнук | правнук / правнучка |
| a=0, b≥4 | (b−2)-пра-онук | пра(пра…)внук — префікс «пра» × (b−2) |
| a=1, b=0 | батько/мати | батько / мати |
| a=2, b=0 | дід/баба | дід / баба |
| a=3, b=0 | прадід | прадід / прабаба |
| a≥4, b=0 | пра…дід | префікс «пра» × (a−2) |
| a=1, b=1 | сиблінг | брат / сестра (див. 4.4 — рідні/зведені) |
| a=2, b=1 | дядько/тітка | дядько / тітка |
| a=3, b=1 | двоюрідний дід | двоюрідний дід / двоюрідна баба |
| a=1, b=2 | племінник | племінник / племінниця |
| a=1, b=3 | внучатий племінник | внучатий племінник / внучата племінниця |
| a=2, b=2 | двоюрідний сиблінг | двоюрідний брат / двоюрідна сестра |
| a=3, b=2 | двоюрідний дядько | двоюрідний дядько / двоюрідна тітка |
| a=2, b=3 | двоюрідний племінник | двоюрідний племінник / двоюрідна племінниця |
| a=3, b=3 | троюрідний сиблінг | троюрідний брат / троюрідна сестра |

**Загальна формула** для a≥1, b≥1: нехай `k = min(a, b)`, `d = |a − b|`:
- Порядок «юрідності» = `k` → префікс: k=1 — «рідний» (не пишеться), k=2 — «двоюрідний», k=3 — «троюрідний», k=4 — «чотириюрідний», далі — «N-юрідний».
- Базове слово залежить від `d` та напрямку:
  - `d = 0` → брат / сестра;
  - `b < a` (B на старшій гілці): d=1 → дядько/тітка; d=2 → дід/баба; d≥3 → пра…дід (префікс «пра» × (d−2)) — з тим самим «юрідним» префіксом;
  - `b > a` (B на молодшій гілці): d=1 → племінник/племінниця; d=2 → внучатий племінник; d≥3 → правнучатий племінник (префікс «пра» × (d−2)).

Реалізувати як чисту функцію:
```csharp
KinshipResult Compute(Person a, Person b, FamilyGraph graph);
// KinshipResult: { RelationCode, DisplayNameUа, PathToCommonAncestor, StepsUp (a), StepsDown (b) }
```
Назву генерувати окремим форматером за інтерфейсом `IKinshipFormatter` (реалізації `UkrainianKinshipFormatter`, `EnglishKinshipFormatter` — див. 2.4 та 4.7), який приймає `(k, d, direction, gender)` і повертає рядок.

### 4.4. Рідні / зведені сиблінги
Для a=1, b=1: якщо в A і B збігаються **обидва** біологічні батьки — «рідний брат/сестра»; якщо тільки батько — «єдинокровний»; тільки мати — «єдиноутробний» (у UI допустимо спрощено: «зведений брат/сестра по батькові/матері»).

### 4.5. Свояцтво (зв'язки через шлюб) — етап 2 (опційно, окрема задача)
Якщо кровного зв'язку немає, шукати шлях виду `A —(кров)— X —(шлюб)— B` або `A —(шлюб)— X —(кров)— B`:
| Зв'язок | Назва |
|---------|-------|
| подружжя | чоловік / дружина |
| батько/мати дружини | тесть / теща |
| батько/мати чоловіка | свекор / свекруха |
| чоловік дочки / дружина сина | зять / невістка |
| брат чоловіка / сестра чоловіка | дівер / зовиця |
| брат дружини / сестра дружини | шурин / своячка |
| чоловік сестри | зять (шваґер) |
| дружина брата | невістка (братова) |
| подружжя дядька/тітки | «дружина дядька», «чоловік тітки» (описово) |
Якщо і так зв'язку немає — повертати «зв'язок не знайдено».

### 4.6. Крайні випадки
- A == B → «це та сама особа».
- Кілька НСП (подружжя-предки: спільні дід і баба) — результат однаковий, брати будь-якого з мінімальною сумою.
- Невідома стать → нейтральне формулювання: «дитина», «сиблінг», «родич 4-го коліна».
- Дуже далекий зв'язок (k > 5) → допустимо «далекий родич (N-юрідний)».
- **Нерідні зв'язки (`ParentRole.Adoptive`/`Step`)** НЕ зараховуються до кровної спорідненості: обхід графа для НСП іде лише біологічними ребрами, тож прийомний батько не стає «предком», а двоє прийомних дітей — «єдинокровними». Прямі назви прийомних/зведених («прийомний батько», «названий син», «вітчим/мачуха») — окрема майбутня задача (див. `IDEAS.md`); наразі такі зв'язки у «Хто кому» дають «зв'язок не встановлено», але лишаються видимими у дереві й на вкладці «Особа».

### 4.7. Англійський форматер (`EnglishKinshipFormatter`)
Алгоритм (пари (a, b)) — спільний для всіх мов; мовоспецифічна лише генерація назви. Англійська система:
- Пряма лінія: father/mother; grandfather/grandmother; префікс great- × (a−2): great-grandfather, great-great-grandfather. Аналогічно son/daughter, grandson, great-grandson.
- Сиблінги: brother/sister; half-brother/half-sister (без поділу на єдинокровних/єдиноутробних — в англійській його немає).
- d = 1, старша гілка: uncle/aunt; d = 2: granduncle (great-uncle)/grandaunt; d ≥ 3: great-granduncle…
- Молодша гілка: nephew/niece; grandnephew/grandniece; great-grandnephew…
- Кузени: формула cousin-ів: ступінь = k − 1 (first/second/third cousin), «removed» = d (once/twice removed). Приклад: (a=3, b=2) → first cousin once removed — те, що українською «двоюрідний дядько».
Ключовий висновок для архітектури: англійські назви **не мапляться 1:1** на українські (одному first cousin once removed відповідають і «двоюрідний дядько», і «двоюрідний племінник» залежно від напрямку) — саме тому форматер отримує сирі (k, d, напрямок, стать), а не перекладає готовий рядок.

## 5. Візуалізація дерева

### 5.1. Режими побудови (від кореневої особи R)
1. **Предки (вгору):** R → батьки → діди → … до вичерпання. Класичне «дерево предків» (кожен вузол має ≤ 2 батьків — виходить бінарне дерево догори).
2. **Нащадки (вниз):** R → діти → онуки → …; поруч із нащадком показувати його подружжя (другого з батьків його дітей).
3. **Повне дерево родичів:** обхід усього зв'язного компонента графа від R; кожна особа отримує підпис родства відносно R (через `KinshipCalculator`). Розкладка — за поколіннями: покоління особи = `StepsDown − StepsUp` відносно R (предки — вище, нащадки — нижче, сиблінги/кузени — на рівні R).

### 5.2. Розкладка (TreeLayoutEngine)
- Алгоритм: пошарова розкладка (layered) — спрощений Reingold–Tilford:
  1. кожній особі призначити рівень (покоління);
  2. рекурсивно порахувати ширину піддерев;
  3. батьків центрувати над дітьми (для режиму «вниз») / дітей під батьками;
  4. подружжя ставити поруч, з'єднувати горизонтальним ребром із «вузлом шлюбу», від якого йдуть лінії до дітей.
- Рушій повертає список `NodeLayout { PersonId, X, Y }` + список ребер `EdgeLayout { FromId, ToId, Kind }` — без WPF-типів.
- Рендеринг: `ItemsControl` на `Canvas` (вузли — DataTemplate, ребра — `Path`/`Line` в окремому шарі) або пряме малювання в `DrawingVisual` (швидше для великих дерев). Рекомендація: почати з `ItemsControl + Canvas`.

### 5.3. Вузол дерева (картка особи)
- Фото (або силует за статтю), «Прізвище Ім'я», роки життя «1954–2020» / «нар. 1988».
- **Підпис родства** відносно кореневої особи (кольоровий бейдж): «я», «мати», «двоюрідна тітка»…
- Клік — вибір; подвійний клік — зробити кореневою особою (перебудова дерева); контекстне меню: редагувати, додати дитину/батьків/подружжя, показати родство з…

### 5.4. Взаємодія з полотном
- Zoom колесом миші (масштаб 0.2–3.0, трансформація `ScaleTransform` відносно курсора).
- Pan перетягуванням правою кнопкою / серединою.
- Кнопки «Вписати в екран», «100%».
- Експорт видимого дерева в PNG (`RenderTargetBitmap`).

**T-3.3. Пояснення шляху.**
Генерація людиночитного ланцюжка: «Оля — дочка Івана; Іван — брат Петра ⇒ Оля — племінниця Петра».
*Критерії:* для кузенів шлях проходить через НСП і читається природно.

**T-3.4. (Опційно) Свояцтво.**
Реалізувати розділ 4.5 як розширення калькулятора з окремим прапорцем «шукати зв'язки через шлюб».
*Критерії:* тесть/теща/свекор/свекруха/зять/невістка/дівер/шурин покриті тестами.

**T-3.5. EnglishKinshipFormatter.**
Друга реалізація `IKinshipFormatter` за розділом 4.7 (система cousin/removed, great-префікси); реєстрація фабрики форматерів за культурою в DI.
*Критерії:* тести ≥ 20 випадків: great-great-grandfather, first cousin once removed (в обох напрямках), second cousin, grandnephew, half-brother; перемикання мови в UI змінює бейджі родства без перезапуску логіки.

### Етап 4. Візуалізація
**T-4.1. TreeLayoutEngine.**
Розкладка за розділом 5.2 для трьох режимів; вхід — `FamilyGraph` + коренева особа + режим + глибина; вихід — координати вузлів і ребра. Юніт-тести на відсутність перекриттів вузлів одного рівня.
*Критерії:* для тестової сімʼї з 4 поколінь вузли не перетинаються; подружжя стоять поруч.

**T-4.2. TreeCanvasControl.**
Рендеринг вузлів (картка з 5.3) і ребер на Canvas; zoom/pan; вибір вузла; подвійний клік = нова коренева особа.
*Критерії:* плавний zoom до курсора; дерево на 200 осіб рендериться < 1 c.

**T-4.3. Панель керування деревом + підписи родства.**
`TreeViewModel`: режим, глибина, перебудова; для режиму «Усі родичі» кожен вузол отримує бейдж з назвою родства (виклик `KinshipCalculator` відносно кореня).
*Критерії:* перемикання Предки/Нащадки/Усі працює без перезапуску; бейджі відповідають тестовим випадкам T-3.2.

**T-4.4. Вкладка «Хто кому».**
Вибір двох осіб → назва зв'язку + пояснення шляху (T-3.3).
*Критерії:* для осіб без зв'язку — коректне повідомлення.

**T-4.5. Експорт дерева в PNG.**
`RenderTargetBitmap` всієї розкладки (не лише видимої частини).
*Критерії:* PNG відкривається, дерево повне й читабельне.

### Етап 5. Сервісні функції та поліровка
**T-5.1. Злиття родин (імпорт з іншого файлу).**
Оскільки формат зберігання і є JSON, окремий «експорт» не потрібен. Натомість: команда «Імпортувати з файлу…» — злиття осіб і зв'язків з іншого `.familytree` у відкритий документ із виявленням потенційних дублікатів (збіг ПІБ + дата народження) та звітом користувачу.

Зіставлення осіб: за `Id` (той самий запис) або за ключем **ПІБ + дата народження**. Для зіставленої особи **порожні** поля цілі доповнюються значеннями з джерела (`DeathDate`, `BirthPlace`, `MaidenName`, `Notes`, `PhotoPath`); **непорожні** розбіжності НЕ перезаписуються, а рахуються як конфлікти у звіті. `Facts` — виняток: список за задумом тримає кілька записів, тож «інша професія» це не суперечність, а другий період життя. Факти джерела, яких немає в цілі, **додаються** й конфліктами не рахуються; точні дублікати відсікає рівність за значенням. Якщо `Id` збігся, але ПІБ+дата обох відомі й **різні** — це різні люди (напр. детерміновані `Id` зі зразків): особа додається з новим `Id`, зв'язки переприв'язуються. Зв'язки при злитті проходять `RelationshipValidator` (цикл, самозв'язок, третій біологічний батько) — недопустимі відхиляються й потрапляють у звіт.

*Примітка:* імпорт GEDCOM (T-5.2) цим шляхом **не** йде — він відкриває новий документ; злити його з наявною родиною можна цією ж командою після збереження у `.familytree`.

*Критерії:* імпорт файлу без перетинів додає всі записи; імпорт того самого файлу двічі не створює дублікатів; дозаповнений родичем файл при повторному імпорті **доповнює** наявних осіб (не втрачає їхніх правок); звіт показує додані/доповнені/конфлікти/відхилені; зв'язок, що утворив би цикл, не додається.

**T-5.2. Імпорт/експорт GEDCOM 5.5.1.**
Двобічний обмін із зовнішніми генеалогічними програмами. Найскладніша задача етапу: формат старий і «брудний» (кілька версій, кодування, кастомні теги), а його модель родини (`FAM`) не збігається з нашою моделлю ребер. Передумова — **T-5.2a** (модель неточних дат), виконана.

*Профіль тегів («робочий»).* Ширший за суто мінімальний: покриває **всі поля моделі, крім `PhotoPath`**, — щоб експорт не втрачав даних, які користувач уже ввів.

- `HEAD`: `SOUR`/`VERS`/`NAME`, `DATE`, `GEDC.VERS 5.5.1`, `GEDC.FORM LINEAGE-LINKED`, `CHAR UTF-8`, `SUBM` (заглушка).
- `INDI`: `NAME` (+`GIVN`, `SURN`, `_MARNM`), `SEX`, `BIRT` (`DATE`, `PLAC`), `DEAT` (`DATE`), `OCCU` (`DATE`, `PLAC`), `RESI` (`DATE`, `PLAC`, `ADDR`, `NOTE`), `NOTE`, `FAMC` (+`PEDI`), `FAMS`, `CHAN.DATE`/`CHAN.TIME`, `_UID`.
- `FAM`: `HUSB`, `WIFE`, `CHIL`, `MARR` (`DATE`), `DIV` (`DATE` або `Y`), `_UID`.
- `TRLR`.

*Поза межами (свідомо).* Медіа (`OBJE`/`FILE`) — `PhotoPath` не експортується й не імпортується; джерела й репозиторії (`SOUR`/`REPO`/`SUBM`-деталі); події та атрибути, крім перелічених вище (`BAPM`, `BURI`, `EDUC`, `RELI`, `TITL`, `CAUS` тощо) — при імпорті пропускаються з лічильником; `ASSO`, `ALIA`; **`DEAT.PLAC`** — у моделі немає поля «місце смерті», тег пропускається (додавання поля — окрема задача, `IDEAS.md`); запис у GEDCOM 7.0; кодування ANSEL; шифровані/архівовані файли. Усе, що поза межами, **ніколи не валить імпорт** — лише збільшує лічильник пропущених тегів у звіті.

Список спожитого ведеться **кваліфікованими шляхами** від запису (`BIRT.PLAC`, `DEAT.DATE`, `CHIL._FREL`), а не голими іменами тегів: той самий `PLAC` під `BIRT` читається, а під `DEAT` — ні, і плоский список цього не розрізняв би. У тег поза профілем підрахунок не спускається — втрачено один запис (`EDUC`), а не три теги (`EDUC` + `EDUC.DATE` + `EDUC.PLAC`).

*Розміщення коду.* Новий проєкт **`FamilyTree.Gedcom`** (`net10.0`, посилається на `FamilyTree.Domain` і `FamilyTree.Storage` — обмін і віддає, і приймає `FamilyDocument`); на нього посилаються `FamilyTree.App` і `FamilyTree.Tests`. Так шар лишається тестованим (`FamilyTree.Tests` — `net10.0`, а не `-windows`), а `FamilyTree.Storage` не обростає чужим форматом. Наявна чернетка `gedcom/` переїжджає туди: `GedcomDate.cs` і `GedcomDateConverter.cs` — у проєкт, `GedcomDateConverterTests.cs` — у `FamilyTree.Tests/Gedcom/`; папка `gedcom/` видаляється.

Склад проєкту:

| Тип | Відповідальність |
|-----|------------------|
| `GedcomLine` (record: `Level`, `Xref`, `Tag`, `Value`) | Один розібраний рядок |
| `GedcomNode` | Вузол дерева записів (`Tag`, `Value`, `Children`) — результат складання рівнів; `UnknownDescendantPaths` віддає шляхи тегів поза профілем для звіту |

**Сутності `Family` в домені не з'являється.** Вона виводиться з ребер і живе лише всередині цього проєкту — інакше довелося б чіпати `FamilyGraph`, `KinshipCalculator`, `TreeLayoutEngine`, `RelationshipValidator` і схему файлу.

*Кодування.* Порядок визначення при читанні:

1. **BOM:** `EF BB BF` → UTF-8; `FF FE` → UTF-16 LE; `FE FF` → UTF-16 BE.
2. Інакше — прочитати `HEAD.CHAR` як ASCII (теги ASCII-безпечні в усіх цільових кодуваннях): `UTF-8` → UTF-8; `UNICODE` → UTF-16; `ANSI`/`WINDOWS-1251`/`CP1251` → Windows-1251; `ASCII` → Windows-1252.
3. **Фолбек:** якщо вибране кодування не декодується суворо (`throwOnInvalidBytes`, як у `ReadTextAsync` для JSON) — повторна спроба Windows-1251, і у звіт іде `GedcomKeys.EncodingFallback` з назвою фактичного кодування. `HEAD.CHAR` у реальних файлах часто бреше, тому фолбек обов'язковий.
4. `ANSEL` → відмова `GedcomKeys.AnselUnsupported` (локалізована, не виняток).
5. `HEAD.CHAR` відсутній → суворий UTF-8, далі фолбек за п. 3.

Запис — завжди **UTF-8 з BOM**, `HEAD.CHAR UTF-8`, кінці рядків `CRLF`, рядок обрізається на 255 байтів через `CONC`, переноси всередині нотаток — `CONT`.

*Мапінг `INDI` ↔ `Person`.*

| Поле моделі | GEDCOM | Експорт | Імпорт |
|---|---|---|---|
| `LastName` / `MaidenName` | `NAME`, `SURN`, `_MARNM` | якщо `MaidenName` задано: `NAME Ім'я По батькові /MaidenName/` + `SURN MaidenName` + `_MARNM LastName`; інакше прізвище в слешах — `LastName` | `SURN` (або текст у слешах). Якщо є `_MARNM` — `MaidenName = SURN`, `LastName = _MARNM`; інакше `LastName = SURN`. Додатковий `NAME` з `TYPE married`/`TYPE maiden` читається як запасний шлях |
| `FirstName` + `MiddleName` | `GIVN` | `GIVN «Ім'я По батькові»` (по батькові — другим словом) | `GIVN` ділиться по **першому** пробілу: перше слово → `FirstName`, решта → `MiddleName` |
| `Gender` | `SEX` | `M` / `F` / `U` | `M`→Male, `F`→Female, решта → Unknown |
| `BirthDate` | `BIRT.DATE` | див. дати | див. дати |
| `BirthPlace` | `BIRT.PLAC` | як є | як є |
| `DeathDate` | `DEAT.DATE` | `DEAT` з `DATE`, коли дата є | як є |
| `Deceased` | `DEAT` (наявність тега) | `1 DEAT Y`, коли особа позначена померлою, а дати немає | будь-який `DEAT` (`Y`, порожній, з підтегами) → `Deceased = true`; `DEAT` без `DATE` додатково рахується у звіті |
| `Facts` (Occupation) | `OCCU` (+`DATE`, `PLAC`) | `Value` — значенням тега, як велить 5.5.1 | значення тега → `Value`, підтеги → `Date`/`Place` |
| `Facts` (Residence) | `RESI` (+`DATE`, `PLAC`, `ADDR`, `NOTE`) | значення тега не пишеться (у 5.5.1 `RESI` — подія без значення): `Place` → `PLAC`, `Value` → `NOTE`. Якщо `Place` порожнє, у `PLAC` іде `Value` — краще нормалізувати, ніж загубити | місце: `PLAC` → `ADDR` (власне значення або склейка `ADR1`/`CITY`/`STAE`/`POST`/`CTRY`) → значення тега. Останнє суперечить стандарту, але так пише чимало програм. `NOTE` → `Value` |
| `Facts` (Other) | — | не пишеться: власного тега в 5.5.1 немає | — |
| `Notes` | `NOTE` (inline) | `CONC`/`CONT` | склеювання `CONC`/`CONT` |
| `Id` | `_UID` | `Guid` у форматі `D` | якщо `_UID` — валідний `Guid`, беремо його як `Id`; інакше новий |

`FirstName` і `LastName` у моделі `required`. Якщо у файлі відповідна частина порожня — підставляється `"?"`, і особа рахується в `GedcomKeys.UnnamedPersons`.

`_UID` — ключове рішення: воно робить зворотний імпорт **власного** експорту точним, бо `FamilyMerger` тоді зіставляє за `Id`, а не за ненадійним ключем «ПІБ + дата народження» (у GEDCOM дата часто лише з роком, і `ToComparable()` перетворив би `1890` на `1890-01-01`, даючи хибні збіги).

*Мапінг `FAM` ↔ ребра — експорт.* Ключ родини — **пара біологічних батьків дитини**. Це коректно за інваріантами домену: `RelationshipValidator` не пускає третього біологічного батька й другого тієї самої статі, а `DocumentIntegrity.RemoveExtraBiologicalParents` дочищає це при завантаженні. Отже, ≤ 2 біологічні батьки на дитину, ≤ 1 відомої статі.

1. Для кожної дитини зібрати її `ParentChildLink` з `ParentRole.Biological` → ключ `(fatherId?, motherId?)`.
2. Згрупувати дітей за ключем → `FAM` з `HUSB`/`WIFE`/`CHIL`.
3. Пройти `SpouseLink`: якщо пара збігається з наявним ключем — домалювати цьому `FAM` теги `MARR`/`DIV`; якщо ні (бездітне подружжя) — створити окремий `FAM` з `HUSB`+`WIFE`+`MARR`.
4. Ребра `Adoptive`/`Step` → **додатковий** `FAMC` у дитини з `PEDI adopted`/`foster`. Якщо усиновлювачі — подружжя, їхній `FAM` уже є з кроку 3; якщо ні — синтетичний `FAM` з одним батьком.
5. Особи без жодних ребер → лише `INDI`, без `FAMC`/`FAMS`.

Розподіл `HUSB`/`WIFE`: `Male` → `HUSB`, `Female` → `WIFE`; якщо обидва `Unknown` (валідатор це дозволяє) — за меншим `Guid`, щоб експорт був відтворюваним.

Порядок і нумерація xref — **детерміновані**, щоб два експорти того самого документа збігалися побайтово: особи сортуються за `(LastName, FirstName, MiddleName, Id)` → `@I1@…`; родини — за `(xref чоловіка, xref дружини)` → `@F1@…`.

Дитина з одним відомим батьком дає `FAM` лише з `HUSB` або лише з `WIFE` — за 5.5.1 це легально.

Повторний шлюб тієї самої пари (два `SpouseLink` із роздільними періодами) дає **один** `FAM` із кількома подіями `MARR`/`DIV`. Це відома втрата: більшість сторонніх програм покаже лише першу подію. Розділяти на два `FAM` не можна — невідомо, яка дитина від якого шлюбу.

*Мапінг `FAM` ↔ ребра — імпорт.*

- Для кожного `CHIL`: `ParentChildLink` від `HUSB` і від `WIFE`. Роль береться з `PEDI` у **дитячому** `INDI.FAMC` (`birth`/`sealing` → `Biological`, `adopted` → `Adoptive`, `foster` → `Step`); якщо є `FAM.CHIL._FREL`/`_MREL` — вони мають пріоритет, бо задають роль окремо для батька й матері. Немає нічого → `Biological`.
- `SpouseLink` створюється **лише** якщо в `FAM` є `MARR` або `DIV`. `FAM` без них — це просто спільні батьки, не подружжя.
- `DIV` з `DATE` → `DivorceDate`; `DIV Y` (без дати) → `Divorced = true`.
- Будь-який `DEAT` → `Deceased = true`; `DEAT` з `DATE` додатково дає `DeathDate`. Зворотно: `1 DEAT Y`, коли прапорець є, а дати немає.
- Кілька пар `MARR`/`DIV` в одному `FAM` → кілька `SpouseLink` тієї самої пари; ті, що дадуть перекриття періодів, відкине `RelationshipValidator` з лічильником у звіті.
- `HUSB`/`WIFE` трактуються як «батько 1 / батько 2» без перевірки статі — файли з одностатевими парами трапляються попри стандарт.

Ця схема робить round-trip **стабільним**: `FAM` з дітьми, але без `MARR`, при зворотному експорті відновлюється з самих дітей (крок 2), тож відсутність `SpouseLink` нічого не губить.

*Дати — `GedcomDate` → `FamilyDate`.*

| `GedcomDate` | `FamilyDate` |
|---|---|
| `Single(Exact)` | `Exact(point)` |
| `Single(About/Calculated/Estimated)` | `Approximate(About/Calculated/Estimated, point)` |
| `Before` / `After` | `Range(Before/After, point)` |
| `Between(from, to)` | `Range(Between, from, to)` |
| `Period` (`FROM…TO`) | `Phrase` (поза межами T-5.2a) |
| `Interpreted` (`INT`) | `Phrase` |
| `Phrase` | `Phrase` |
| будь-яка з `IsBce`, `DualYear`, календарем `Hebrew`/`French`, або з `Year == null` | `Phrase` |

Кожна дата, що потрапила в `Phrase` через непідтримувану форму, зберігає **сирий вираз** у `FamilyDate.OriginalGedcom`. `Calendar.Julian` мапиться прямо в `DatePoint.Calendar`.

Зворотний напрям: якщо `OriginalGedcom` не порожній — пишеться **як є** (точний round-trip); інакше генерується за `Kind`: `Exact` → `[DD] MON YYYY` за наявною точністю, `Approximate` → `ABT`/`CAL`/`EST` + точка, `Range` → `BEF`/`AFT` + точка або `BET … AND …`, `Phrase` → текст у дужках. Юліанська точка отримує префікс `@#DJULIAN@`.

*Санітарія і звіт.* Зібраний `FamilyDocument` **обов'язково** проганяється через наявний `DocumentIntegrity` — той самий, що чистить JSON-файли (висячі й самозв'язки, дублі, цикли, зайві біологічні батьки, структурно биті дати, небезпечні шляхи). Його `DocumentIssue` лягають у звіт поряд із власними лічильниками імпорту.

`GedcomImportReport`: `Persons`, `Families`, `ParentChildLinks`, `SpouseLinks`, `UnnamedPersons`, `SkippedTags` (`IReadOnlyDictionary<string,int>` — **кваліфікований шлях** тега від запису (`DEAT.PLAC`, `RESI.ADDR.CITY`) → кількість; в UI показуються 5 найчастіших), `SkippedRecords`, `EncodingFallback` (фактичне кодування або `null`), `RepairedIssues` (`IReadOnlyList<DocumentIssue>`).

Ключі `GedcomKeys` (за зразком `FileErrorKeys` — шар не знає про resx, віддає ключ + аргументи):

- помилки читання: `GedcomError_NotGedcom` (немає `0 HEAD`), `GedcomError_AnselUnsupported`, `GedcomError_UnsupportedVersion` (`HEAD.GEDC.VERS` 7.x), `GedcomError_BadEncoding`; помилки файлової системи перевикористовують `FileErrorKeys.NotFound`/`AccessDenied`/`Io`;
- попередження: `GedcomWarn_EncodingFallback`, `GedcomWarn_SkippedTags`, `GedcomWarn_UnnamedPersons`, `GedcomWarn_DeathWithoutDate`, `GedcomWarn_RejectedLinks`.

*Інтерфейс.* У меню «Файл» — два нові пункти окремо від наявного «Імпорт» (він лишається для `.familytree`): **«Імпорт GEDCOM…»** (`Menu_ImportGedcom`) і **«Експорт GEDCOM…»** (`Menu_ExportGedcom`).

- Імпорт **завжди відкриває новий документ** (як `Open`: спершу `PromptSaveIfDirtyAsync()`), заголовок — з імені файлу, документ одразу `IsDirty` (у `.familytree` ще не збережений). Злиття з поточною родиною свідомо не робиться: для цього є наявна команда «Імпорт» після збереження у власний формат.
- Після імпорту — вікно звіту через `IDialogService.ShowMessage` (за зразком `MainViewModel.MergeExtras`: рядки додаються лише для ненульових лічильників).
- Експорт — `AskSavePath` з фільтром `File_FilterGedcom`. **Потрібна дрібна правка інфраструктури:** `IDialogService.AskSavePath` зараз хардкодить `DefaultExt = ".familytree"` — додати параметр розширення.
- Нові рядки — в **обидва** resx.
- Читання й запис — `async`, курсор очікування. Прогрес і скасування поза межами (5 000 осіб читаються менше секунди).

*Порядок виконання (порціями, зі зупинкою після кожної).*

1. **Каркас і читання.** Проєкт `FamilyTree.Gedcom`, перенос чернетки, `GedcomLine`/`GedcomNode`/`GedcomReader`/`GedcomEncodingDetector` (`GedcomWriter` — у Частині 2, разом із його споживачем). Тести: рівні й вкладення, `CONC`/`CONT`, екранування `@@`, усі кодування з п. 1–5, файл без `TRLR`, файл із зайвими порожніми рядками.
2. **Експорт.** `GedcomWriter`, `GedcomFamilyBuilder` (напрям назовні), `GedcomDateMapper` (назовні), `GedcomExporter`. Тести: виведення `FAM` для крайніх випадків (один батько; бездітне подружжя; неодружені співбатьки; усиновлення; повторний шлюб; обидва батьки `Unknown`; особа без ребер; пара з дітьми **і** шлюбом), детермінованість xref, round-trip записаного через `GedcomReader`. Родини-фікстури будуються **кодом** (за зразком `KinshipTestFamily`), а не читанням із `samples/`: тест не має тягтися до файлів поза своїм проєктом, і в самому тесті видно, яку конфігурацію він перевіряє. Перевірка на реальних `samples/*` — у Частині 3, де вона й потрібна.
3. **Імпорт.** `GedcomImporter`, `GedcomDateMapper` (усередину), прогін через `DocumentIntegrity`, звіт. Тести: round-trip, брудні файли, невідомі теги, `PEDI`.
4. **UI.** Меню, фільтри, параметр розширення в `AskSavePath`, resx в обидва файли, вікно звіту.

*Критерії.*

- **Round-trip (автотест).** Для кожного `samples/*.familytree` експорт → імпорт дає документ, ідентичний вихідному за складом осіб (ПІБ з по батькові, дівоче, стать, чотири дати, місце народження, нотатки, `Deceased`), ребер (з `ParentRole`) і подружжів (з датами та `Divorced`). Порівняння за `_UID`, тому зіставлення осіб точне.
- **Детермінованість.** Два експорти того самого документа дають побайтово однаковий файл.
- **Сумісність назовні (ручна).** Експортований файл відкривається без помилок у **Gramps** і показує дерево з правильними поколіннями, іменами й датами.
- **Сумісність усередину.** Щонайменше один реальний сторонній `.ged` у `samples/gedcom/` імпортується в несуперечливий документ: `DocumentIntegrity` не повідомляє про критичні дефекти, дерево будується, «Хто кому» рахує родство.
- **Кирилиця.** Файл у Windows-1251 із неправдивим `HEAD.CHAR UTF-8` читається без «кракозябр», а у звіті стоїть позначка фолбеку кодування.
- **Стійкість.** Невідомі теги, відсутній `TRLR`, обрізаний файл і подвійні `@@` не валять імпорт; ANSEL і GEDCOM 7.0 дають зрозумілу локалізовану відмову, а не виняток.

**T-5.2a. Модель неточних дат + контрол `FamilyDateEditor` (передумова T-5.2).**
Поточний `DateOnly?` тримає лише повну точну дату — замало для реальних даних і, зокрема, для імпорту GEDCOM (часткові, приблизні, діапазони, текст). Задача вводить доменний тип дати та єдиний UI-контрол, що заміняє `DatePicker` скрізь (дати народження, смерті, шлюбу, розлучення). Робиться **до** T-5.2, бо мапінг GEDCOM-дат спирається на цю модель. **Поза межами:** роки до н.е. (`B.C.`); неґрегоріанські календарі, **окрім юліанського**; GEDCOM-періоди `FROM…TO`; інтерпретовані `INT` і подвійні роки (`1699/00`) — при імпорті зводяться до фрази / оригінального рядка.

*Модель.* Незмінний value-тип `FamilyDate` (Domain) заміняє `DateOnly?` у полях дат; `null` = «невідомо». Форми (`kind`): **Exact** — одна дата-точка з точністю день/місяць/рік («звичайна» = день, «часткова» = рік або місяць+рік); **Approximate** — точка + кваліфікатор `About`/`Calculated`/`Estimated` (GEDCOM `ABT`/`CAL`/`EST`); **Range** — `Before`/`After`/`Between` (`BEF`/`AFT`/`BET…AND`), одна або дві точки; **Phrase** — лише вільний текст. Дата-точка (`DatePoint`): `Year` (обов'язк.), `Month?`, `Day?`, `Calendar` (`Gregorian`/`Julian`). Опційне приховане поле `OriginalGedcom` — сирий GEDCOM-вираз, заповнюється лише при імпорті, використовується при експорті «як є» (round-trip), у UI не показується й скидається при ручному редагуванні. Допоміжні члени `EffectiveYear`/`ToComparable()` дають представницьке значення для сортування й м'яких попереджень (Phrase → «немає», порівняння пропускається). `KinshipCalculator` **не** торкається (спорідненість — за структурою графа).

*Сховище.* `schemaVersion` 1→2; дати як об'єкти (див. §3.5); міграція `IFormatMigration (v1→v2)` перетворює старі ISO-рядки на `kind:"exact"` тихо, без запису у звіт полагоджень; `DocumentIntegrity` відкидає структурно биту дату (напр. `range` без меж) у `null` зі звітом.

*Контрол.* `FamilyDateEditor` (UserControl, DP `Value : FamilyDate?`): зверху — вибір типу дати (звичайна/часткова/приблизна/діапазон/фраза), за замовчуванням «звичайна» з `DatePicker`; нижче — поле вводу, що змінюється за типом; окремий перемикач календаря (григоріанський/юліанський), ортогональний до типу, для типів із датою-точкою. Порожня дата дозволена. Показ — `FamilyDateFormatter` (uk/en): «14.03.1980», «березень 1850», «1850», «≈1850», «до 1900», «1980–1985», «(текст)». Локалізація — обидва resx; мова вбудованого `DatePicker` — через `UiLanguage`; кольори — `DynamicResource`. М'які попередження валідатора (вік, смерть<народження) — на `EffectiveYear`, пропускаються для нерезолвних (Phrase).

*Порядок:* (1a) модель + тести; (1b) заміна полів + серіалізація v2 + міграція + плюмбінг (збірка зелена, точні дати); (2) контрол + форматер + заміна `DatePicker`.

*Критерії:* за замовчуванням контрол — `DatePicker` (звичайна дата); перемикання типу міняє поле вводу; порожня дата дозволена. Старі `.familytree` (v1) відкриваються без утрат (міграція на `exact`). Кожен тип зберігається й читається ідентично (save→load). Показ uk/en коректний і оновлюється при зміні мови. Наявні вікові попередження працюють для exact/partial/approx, пропускаються для phrase. Модель придатна для прямого мапінгу в/з GEDCOM DATE у T-5.2.

## 10. Ризики та зауваги
- **Назви родства** — найчутливіша частина: обов'язково вести таблицю тестів (T-3.2, T-3.5) і поповнювати її при кожному знайденому неточному формулюванні. Пам'ятати, що назви для різних мов не мапляться 1:1 (розділ 4.7).
- **Розкладка дерева** для режиму «Усі родичі» складніша за класичні дерева (граф, а не дерево): на MVP допустимо групувати за поколіннями рядами й мінімізувати перетини ребер евристично.
- **Продуктивність Canvas:** якщо > 500 вузлів — перейти з ItemsControl на DrawingVisual (закладено в T-4.2 як план Б).
- **Цілісність файлу:** атомарний запис і бекапи (розділ 3.5) — не опція, а обов'язкова частина T-1.4; втрата родинного архіву — найгірший можливий баг застосунку.
- **Дані реальних людей:** дані зберігаються локально у файлі користувача; у документації зазначити, що вони нікуди не передаються.
