## 0.9.4 — неточні дати (T-5.2a) + сім багів

### T-5.2a — модель неточних дат і контрол `FamilyDateEditor`

Формат файлу піднято до **v2** із вбудованою міграцією v1→v2. Повна постановка — у специфікації,
§7, T-5.2a (§3.1/§3.2/§3.5 теж оновлені). Порядок: 1a → 1b → 2.

**Зроблено — Частина 1a (доменна модель):**
- `FamilyTree.Domain/FamilyDate.cs` — незмінний record: `FamilyDate` (Kind: `Exact`/`Approximate`/`Range`/`Phrase`) + `DatePoint` (Year + опц. Month/Day + `DateCalendar` Gregorian/Julian) + enum-и (`DateApproximation` ABT/CAL/EST, `DateRangeKind` Before/After/Between, `DatePrecision`). Фабрики, `EffectiveYear`, `ToComparable()` (DateOnly? — представницька для сортування/порівнянь; для Phrase = null), `IsStructurallyValid()`, приховане `OriginalGedcom` (round-trip). **Неявний оператор `DateOnly → FamilyDate`** (C# піднімає й до `DateOnly? → FamilyDate?`) — щоб старий код/тести з `new DateOnly(...)` компілювались без змін.
- Тести: `FamilyTree.Tests/Domain/FamilyDateTests.cs`.

**Зроблено — Частина 1b (заміна полів + сховище + міграція):**
- `Person.BirthDate/DeathDate`, `SpouseLink.MarriageDate/DivorceDate` → `FamilyDate?`.
- Формат файлу **v2**: `FamilyDateDto`+`DatePointDto` у `FamilyFileDto`; мапінг у `DocumentMapper` (kind/y/m/d/cal/q/range/from/to/text/gedcom). `JsonFamilyStorage.CurrentSchemaVersion = 2`.
- **Міграція** `Serialization/FormatMigrationV1ToV2.cs` (ISO-рядок дати → `{"kind":"exact",...}`), підключена як **вбудована** в дефолтний ctor `JsonFamilyStorage` (`BuiltInMigrations`) — тож App і всі тести отримують її автоматично.
- `DocumentIntegrity.SanitizeDates` (структурно биті дати → null, ключ `FileRepair_BadDates` у обидва resx). `PeriodOverlaps`, `PersonQuery` (сорт), `RelationshipValidator` (вікові попередження), `PersonCard`/`PersonYearsConverter` — на `ToComparable()`/`EffectiveYear`. `FamilyMerger` — ключ ідентичності на `ToComparable()`.
- Редактори (`PersonEditorViewModel`, `RelationshipEditorViewModel`) поки лишились на `DatePicker` (лише точна дата) через конвертери `FamilyDate?`↔`DateTime?` — App компілюється; повноцінний ввід — у Частині 2.
- Тести: `FamilyTree.Tests/Storage/FamilyDateStorageTests.cs` (round-trip кожного типу + міграція); оновлені асерти в `JsonFamilyStorageTests`/`FamilyMergerTests` (обгорнуто в `FamilyDate.Exact(...)`).
- Стан: збірка й тести **зелені** (підтверджено локально).

**Уроки (щоб не повторювати):** `FamilyDate` — **клас (record)**, а не структура, тож `FamilyDate?`
це НЕ `Nullable<>`: немає `.Value`/`.HasValue` (пиши сам об'єкт; перевірка `is { }`/`is not null`;
порівняння прямо `==`/`!=`). Заміна типу дати ловиться не лише за `.BirthDate` тощо, а й там, де тип
«зашитий» у тип-параметрах (`HashSet<(…, DateOnly?)>` у `DocumentIntegrity.RemoveDuplicateLinks`).
App-VM у наявному тест-проєкті НЕ тестуються (Tests = `net10.0`, App = `net10.0-windows`).

### Баги

- **B-13** — санітизація `PhotoPath` (зроблено, закомічено).
- **B-18** — другий біо-батько при `Gender.Unknown` (зроблено: правило «≤2 біо-батьки, U+U ок, M+F+U ні» у валідаторі й `DocumentIntegrity`).
- **B-25** — локалізація повідомлень про помилки імпорту: гілка catch в `MainViewModel.Import` тепер через `DescribeFileError(ex)` (як відкриття/збереження), а не сирий `ex.Message`. Звірити збірку локально.
- **B-02** — демо-родина народжувала людей у майбутньому. Крок «батьки→дитина» звужено до 22–28 (середнє ~25 = `GenerationGap`, прибрано систематичний дрейф); `RandomDate` тепер обрізає будь-яку дату до сьогодні (гарантія для народження/шлюбу/смерті). Тест `No_dates_are_in_the_future` (4/40, 5/120, 8/2000, по 5 насінин).
- **B-05** — незбережені зміни губилися при завершенні сеансу Windows (SessionEnding не проходить через OnClosing). Додано `App.OnSessionEnding` + синхронний `MainViewModel.PromptSaveIfDirtyBlocking()` (шлях — на UI-потоці, запис — блокуюче через `Task.Run(...).GetAwaiter().GetResult()`, щоб уникнути дедлоку); `MainWindow.AllowClose()` не дає перепитати вдруге під час shutdown.
- **B-19** — редагування дат подружжя обходило валідатор. `MainViewModel.EditSpouse` тепер будує кандидат-`SpouseLink` і проганяє через `_validator.ValidateSpouse(candidate, others)` + `Accept(...)` (як AddSpouse). У `ValidateSpouse` додано м'яке попередження `Validation_DivorceBeforeMarriage` (розлучення раніше шлюбу) — новий ключ у `ValidationKeys` і обидва resx; тест `Divorce_before_marriage_is_warning`.
- **B-06** — корінь дерева відкочувався на `SelectedPerson` після зміни вмісту. Додано подію `TreeViewModel.RootChanged` (спрацьовує в `SetRoot`, коли корінь реально змінився й не null); `MainViewModel.OnTreeRootChanged` синхронізує `SelectedPerson` із новим коренем (подвійний клік по вузлу) → список/вкладка «Особа»/наступний `RefreshPersons()` більше не «стрибають» назад. Рекурсії немає: повторний `SetRoot(sameId)` рано виходить. Примітка: дрібний другий симптом (втрата підсвітки після одиночного кліку при зміні вмісту) не чіпав — це `Render()` перестворює `Nodes`, суміжне з B-07.
- **B-07** — фриз від перебудови дерева на кожну зміну виділення/вмісту. Зроблено два головні під-фікси: (1) **дебаунс виділення** — `MainViewModel.DebounceSelection()` (120 мс, скасовуваний CTS як пошук) застосовує лише фінальну особу, гортання стрілками не будує дерево щоразу; (2) **гейт активної вкладки** — `TreeViewModel.IsActive` (+`_rebuildPending`): поки вкладка «Дерево» неактивна, `Rebuild()` відкладається, при поверненні будується один раз; вмикає `MainWindow.MainTabs_SelectionChanged` (індекс 1). **Не зроблено (лишок B-07, некритично):** LRU-кеш бейджів по `(rootId, relativeId)`, кеш `byId`/`childCounts` у `RefreshRelations`, і суміжний **B-27** (кеш предків кореня) — можна взяти пізніше пачкою перф-оптимізацій.
