### B-01. `DatePicker` парсить дати в en-US незалежно від мови інтерфейсу

**Файли:** `FamilyTree.App/PersonEditorWindow.xaml:53` і `:64`,
`FamilyTree.App/RelationshipEditorWindow.xaml:117` і `:124`.
Корінь — відсутність перевизначення в `App.xaml.cs` (перевірено grep'ом: `LanguageProperty`,
`XmlLanguage`, `ConverterCulture`, `xml:lang` — **жодного входження** у власному коді).

```xml
<!-- PersonEditorWindow.xaml:53 -->
<DatePicker SelectedDate="{Binding BirthDate}" HorizontalAlignment="Left" MinWidth="200" />
```
```csharp
// Localization/LocalizationService.cs:157-163 — виставляє культуру ПОТОКУ
Thread.CurrentThread.CurrentCulture = option.FormattingCulture;
```

**Чому баг.** У WPF `FrameworkElement.Language` (xml:lang) має метадані за замовчуванням `en-US`
і **не залежить** від `Thread.CurrentCulture`. `DatePicker`/`Calendar` форматують і парсять саме за
`Language`. Отже вся робота `LocalizationService` на дати у формах не впливає.

**Відтворення.** Мова UI — українська. «Додати особу» → у полі «Дата народження» ввести `03.04.1980`
(3 квітня). DatePicker парсить як en-US → **4 березня 1980**. Дата йде в документ; картка особи
(`PersonCard.FormatDate`) виводить її вже за `CurrentCulture` → `04.03.1980`. Користувач бачить іншу
дату, ніж ввів, без жодного попередження. Плюс англійські назви місяців і тиждень із неділі.

**Фікс.** У статичному конструкторі `App` (до створення вікон):
```csharp
FrameworkElement.LanguageProperty.OverrideMetadata(
    typeof(FrameworkElement),
    new FrameworkPropertyMetadata(
        XmlLanguage.GetLanguage(CultureInfo.CurrentCulture.IetfLanguageTag)));
```
Мова перемикається вживу, тож це треба повторювати в обробнику `LanguageChanged` для вже відкритих
вікон (`window.Language = XmlLanguage.GetLanguage(...)` по `Application.Current.Windows`).
Увага: `uk`/`en` — **нейтральні** культури; резолвити у специфічні (`uk-UA`, `en-US`).

### B-02. Демо-родина масово створює людей, народжених у майбутньому

**Файл:** `FamilyTree.Domain/Seeding/DemoFamilyGenerator.cs:61-62`, `:87`, `:95`

```csharp
var youngestBirthYear = _currentYear - 16;
var baseYear = youngestBirthYear - (_opts.Generations - 1) * GenerationGap;  // GenerationGap = 25
...
var childBirth = couple.ParentsBirthYear + _rnd.Next(24, 43); // фактично 24..42, середнє 33
...
var marryYear = childBirth + _rnd.Next(20, 30);
```

**Чому баг.** `baseYear` рахується з припущення «крок поколінь = 25 років», а фактичний крок —
рівномірний на [24, 42], середнє 33. Різниця у 8 років накопичується щопокоління. Верхньої межі
на `childBirth` немає взагалі.

Симуляція логіки (2026 рік, 5 сідів):

| Generations | MaxPersons | Осіб | Народжених після 2026 | Макс. рік |
|---|---|---|---|---|
| 4 (за замовчуванням) | 40 | ~40 | **~18 %** | 2051 |
| 5 | 120 | ~120 | **~24 %** | 2069 |
| 8 | 2000 | ~2000 | **~38 %** | 2092 |

Дати шлюбу ще гірші (`marryYear` = народження + 20..29). Це видно на першому ж екрані застосунку
і прямо суперечить власній валідації (`ValidationKeys.ParentYoungerThanChild`).

**Фікс.**
```csharp
private int ClampYear(int year) => Math.Min(year, _currentYear);
...
var childBirth = ClampYear(couple.ParentsBirthYear + _rnd.Next(24, 43));
var marryYear  = ClampYear(childBirth + _rnd.Next(20, 30));
```
Плюс привести `GenerationGap` до фактичного середнього (33) або звузити `_rnd.Next(24, 43)` до
`(22, 29)`. Закріпити тестом: `result.Persons.All(p => p.BirthDate <= DateOnly.FromDateTime(DateTime.Today))`.

### B-03. BOM вимикає захист від неправильного кодування — крякозябри тихо зберігаються назад

**Файл:** `FamilyTree.Storage/JsonFamilyStorage.cs:110-111`

```csharp
var encoding = new UTF8Encoding(encoderShouldEmitUTF8Identifier: false, throwOnInvalidBytes: true);
using var reader = new StreamReader(path, encoding, detectEncodingFromByteOrderMarks: true);
```

**Чому баг.** `StreamReader.DetectEncoding()` при виявленні BOM **замінює** передане кодування на
статичний `Encoding.UTF8` — екземпляр із **replacement**-фолбеком, а не з `throwOnInvalidBytes: true`.
Тобто весь сенс рядка 110 (і фікса S-D16 зі старого аудиту) зникає рівно для файлів із BOM: невалідні
байти знову тихо стають `U+FFFD`.

Наслідок незворотний: `U+FFFD` — валідний символ у JSON, парсинг проходить, `DocumentIntegrity` нічого
не бачить, документ відкривається, а перше ж збереження записує крякозябри на диск і зсуває бекапи.
Оригінальні байти зникають назавжди.

**Відтворення.** Файл, збережений як «UTF-8 з BOM», де частина тіла — в Windows-1251 (типово: чужий
експортер, конвертер, часткове відновлення, редактор що зберіг BOM але тіло в ANSI). Наявний тест
`CorruptFileTests.Non_utf8_file_reports_bad_encoding` (`CorruptFileTests.cs:132-146`) пише ті самі
байти **без** BOM, тому проходить і дірку не показує.

**Фікс.**
```csharp
var bytes = await File.ReadAllBytesAsync(path, cancellationToken).ConfigureAwait(false);
var span = bytes.AsSpan();
if (span.StartsWith(Encoding.UTF8.Preamble)) span = span[Encoding.UTF8.Preamble.Length..];
var strict = new UTF8Encoding(false, throwOnInvalidBytes: true);
return strict.GetString(span);   // кине DecoderFallbackException
```
Або `new StreamReader(stream, strict, detectEncodingFromByteOrderMarks: false)` з ручним пропуском преамбули.

> ⚠️ Поведінку `DetectEncoding` встановлено читанням реалізації `StreamReader` у runtime. Оскільки .NET
> тут не запускається, підтвердіть одним тестом (див. T-4 у розділі тестів). Сам фікс безпечний у будь-якому разі.

### B-04. Злиття не переносить правок наявних осіб; звіт при цьому виглядає успішним

**Файл:** `FamilyTree.Storage/FamilyMerger.cs:60-85` `[було в AUDIT.md — S-B10, досі відкрито]`

```csharp
if (existingIds.Contains(person.Id))
{
    remap[person.Id] = person.Id; // той самий запис уже є (напр. повторний імпорт)
    duplicates++;
    continue;
}
var key = IdentityKey(person);
if (key is not null && existingByKey.TryGetValue(key, out var matchId))
{
    remap[person.Id] = matchId; // збіг ПІБ + дати народження → зливаємо
    duplicates++;
    continue;
}
```

**Чому баг.** Слово «зливаємо» в коментарі не відповідає коду: жодного зливання полів немає — запис
із джерела просто **відкидається**. Це ламає головний генеалогічний сценарій продукту.

**Відтворення 1.** Ви дали копію файлу родичу. Родич заповнив 40 осіб: дати смерті, місця народження,
дівочі прізвища, нотатки. Ви робите «Імпорт». Усі `Id` збігаються → `duplicates++` → **всі 40 правок
відкинуто**. Діалог показує «додано 0, дублікатів 40» (`MainViewModel.cs:261-268`) — виглядає як
коректне «нічого нового», хоча ви щойно втратили всю його роботу.

**Відтворення 2 (гірше — колізія Id).** `Clone` (`FamilyMerger.cs:166-181`) зберігає `Id = p.Id`, тобто
перенумерації при колізії немає в принципі. У репозиторії лежать зразки з **детермінованими** Id
(`samples/rodyna-kovalenkiv.familytree` — `10000000-0000-4000-8000-…`). Два документи, породжені від
таких зразків, при імпорті ототожнять **різних людей**, і зв'язки будуть переприв'язані до сторонньої
людини — тихо, без попередження.

**Фікс.**
1. При збігу `Id` порівнювати `IdentityKey`; розбіжність → трактувати як **іншу** особу: клон із **новим**
   `Guid` і переприв'язка через `remap` (механізм уже є).
2. Для справжніх дублікатів — заповнювати порожні поля цілі значеннями з джерела (`DeathDate`,
   `BirthPlace`, `MaidenName`, `Notes`, `PhotoPath`), а розбіжності непорожніх — у `MergePlan.Conflicts`.
3. Додати в `MergeReport` поля `UpdatedPersons` і `Conflicts`, щоб діалог не рапортував «все добре».

### B-05. Незбережені зміни губляться при завершенні сеансу Windows

**Файли:** `FamilyTree.App/MainWindow.xaml.cs:17-33` (єдиний захист); `SessionEnding` у проєкті —
**0 входжень** (перевірено grep'ом).

Усі «звичайні» шляхи виходу закриті коректно — перевірено кожен:

| Шлях | Питає про збереження |
|---|---|
| Хрестик / Alt+F4 | ✅ `OnClosing` |
| Меню → Вихід (`MainViewModel.cs:335`) | ✅ |
| Новий / Відкрити / Останні файли (`:205`, `:214`, `:234`) | ✅ |
| Запуск із файлу (асоціація) `:343`, Демо-родина `:293` | ✅ |
| **Завершення роботи / вихід із сеансу Windows** | ❌ |

**Чому баг.** При `WM_QUERYENDSESSION` WPF піднімає `Application.SessionEnding`; якщо його не скасувати,
викликається `Application.Shutdown()`, який закриває вікна **ігноруючи `e.Cancel`** у `Closing`.
Користувач із незбереженим деревом натискає «Перезавантажити» у Windows — застосунок мовчки
закривається, дані втрачено.

**Фікс.** В `App`:
```csharp
SessionEnding += (_, e) =>
{
    var vm = _host.Services.GetRequiredService<MainViewModel>();
    if (vm.HasUnsavedChanges && !PromptSaveSync(vm)) e.Cancel = true;
};
```
`SessionEnding` не дає чекати на `await`, тож потрібна синхронна гілка `PromptSaveIfDirty`
(Windows дає ~5 с на реакцію).

### B-06. Корінь дерева самовільно відкочується на `SelectedPerson`

**Файл:** `FamilyTree.App/Controls/TreeCanvasControl.xaml.cs:33-34`

```csharp
Surface.NodeSelected  += (_, node) => Vm?.SelectNode(node.PersonId);
Surface.NodeActivated += (_, node) => Vm?.SetRoot(node.PersonId);
```

`Vm` тут — `TreeViewModel` (`DataContext="{Binding Tree}"`, `MainWindow.xaml:306`).
`MainViewModel.SelectedPerson` і `_lastSelectedId` при цьому **не змінюються**.
А `RefreshPersons()` наприкінці робить (`MainViewModel.cs:1021`): `ApplySelection(SelectedPerson)`
→ `_tree.SetRoot(SelectedPerson.Id)`.

**Відтворення.**
1. У лівому списку виділити особу **А** → корінь дерева = А.
2. Вкладка «Дерево», подвійний клік по вузлу **Б** → корінь = Б (заявлена фіча).
3. Зробити будь-що, що змінює вміст або список (додати особу, змінити сортування, ввести текст
   у пошук, видалити зв'язок) → `ContentChanged` → `RefreshPersons()` → `ApplySelection(А)` →
   **дерево стрибає назад на А**.

Другий симптом того ж кореня: одиночний клік ставить лише `node.IsSelected`, а `Render()`
(`TreeViewModel.cs:280`) перестворює всю колекцію `Nodes` — підсвітка зникає при першій зміні вмісту.
І вкладка «Особа» весь час показує родичів А, а не Б.

**Фікс.** Прокинути вибір із дерева назад у `MainViewModel` — подією `TreeViewModel.RootChanged`,
на яку `MainViewModel` виставляє `SelectedPerson` (під `_suppressSelectionSync`, щоб не спричинити
зайвий `Rebuild`). Альтернатива — прив'язати `TreeCanvasControl` до `MainViewModel` і викликати команду.

### B-07. Кожна зміна виділення в списку = повна перебудова графа + перерахунок родства для всіх вузлів

**Файли:** `FamilyTree.App/ViewModels/MainViewModel.cs:904-913`; `ViewModels/TreeViewModel.cs:221-250`, `416-426`

```csharp
// MainViewModel.cs:904
private void ApplySelection(Person? value)
{
    RefreshRelations();                 // O(n) словник + GroupBy по ВСІХ зв'язках
    if (value is not null) { _lastSelectedId = value.Id; _tree.SetRoot(value.Id); }  // → Rebuild()
}
```
```csharp
// TreeViewModel.cs:237
if (_badgeRootId != rootId) { _badges.Clear(); _badgeRootId = rootId; }   // кеш родства скинуто
_persons = doc.Persons.DistinctBy(p => p.Id).ToDictionary(p => p.Id);
_layout  = _engine.Build(graph, rootId, Mode, Depth);
Render();                               // Badge() для КОЖНОГО вузла → KinshipCalculator.Compute
```

**Чому баг.** `ListBox.SelectedItem` (`MainWindow.xaml:165`) двостороння, тож **кожне натискання
стрілки вниз** запускає: `RefreshRelations()` (500 записів + `GroupBy` по всіх зв'язках) → новий
`FamilyGraph` → `TreeLayoutEngine.Build` → `Render()` із щойно скинутим кешем бейджів, тобто
`KinshipCalculator.Compute` для **кожного** вузла (за коментарем `TreeViewModel.cs:66-68` — ~5 обходів
графа на вузол) → перезаповнення 4 `ObservableCollection`.

Дерево будується **навіть коли активна вкладка «Особа» чи «Хто кому»**: `TreeViewModel` — синглтон,
підписаний на сесію, про видимість вкладки не знає. Затиснута стрілка вниз на 500 особах із
«Глибина = 0 (усі)» дає багатосекундне зависання без індикатора.

**Фікс.**
- Дебаунс виділення (як для пошуку, `SearchDebounceMs`) перед `SetRoot`/`RefreshRelations`.
- Не перебудовувати дерево, коли вкладка «Дерево» неактивна: прапорець «брудно» + `Rebuild()` при активації.
- `RefreshRelations()` — тримати `byId`/`childCounts` як кеш, інвалідований на `ContentChanged`.
- Кеш бейджів не скидати повністю: `Dictionary<(rootId, relativeId), string>` або LRU.
- Разом із B-27 (кешування предків кореня) це прибирає більшу частину вартості.

### B-08. `_session.FilePath` виставляється ДО успішного запису

`FamilyTree.App/ViewModels/MainViewModel.cs:374-383`

```csharp
if (_dialogs.AskSavePath(FileFilter, suggested) is not { } path) return false;
_session.FilePath = path;            // ← ще нічого не записано
return await WriteAsync(path);
```

**Відтворення.** Новий документ → «Зберегти як» → шлях у захищеній теці (`C:\Program Files\…`) →
`UnauthorizedAccessException`, повідомлення показано. Але `_session.FilePath` уже дорівнює цьому шляху:

WPF викликає `OnExit` і одразу після повернення завершує диспетчер (`Dispatcher.CriticalInvokeShutdown`).
`async void` повертає керування на першому `await`, який не завершився синхронно; продовження ставиться
в чергу, яку вже ніхто не прокачає. Тоді **не виконуються** `_host.Dispose()`, `Log.CloseAndFlush()` і
`base.OnExit(e)` → останні записи журналу губляться, а `MainViewModel.Dispose()` / `TreeViewModel.Dispose()`
(викликаються саме через `_host.Dispose()`) не спрацьовують ніколи.

Тобто на питання «чи справді Dispose викликається» відповідь — **ні**. Витоку зараз немає лише тому, що
всі підписники — `Singleton` із часом життя застосунку. `Dispose()` у `MainViewModel.cs:1134-1139` і
`TreeViewModel.cs:496-501` — коректний, але мертвий код.

> ⚠️ Якщо `Host.StopAsync()` завершується синхронно (ймовірно для хоста без `IHostedService`), проблеми
> зараз немає. Але це крихка залежність: додавання будь-якого `IHostedService` мовчки зламає вихід.

**Фікс.**
```csharp
protected override void OnExit(ExitEventArgs e)
{
    Log.Information(...);
    try { _host.StopAsync(TimeSpan.FromSeconds(5)).GetAwaiter().GetResult(); } catch { }
    _host.Dispose(); AppLog.Shutdown(); base.OnExit(e);
}
```

## Прогалини в тестах

### Domain (20 файлів — покриття загалом добре)

1. **Цикл у графі** (`A → B → A`) — жоден тест не будує. Захист у коді є, але не зафіксований → легко зламати рефакторингом.
2. **Самозв'язок** на рівні `FamilyGraph` (є лише на рівні `RelationshipValidator`).
3. **Два `SpouseLink` на ту саму пару** — нема жодного тесту на `IsSpouseActive` за конфліктних зв'язків (B-16).
4. **Висячі посилання** та **дублікат `Person.Id`** — гілки `continue`/`DistinctBy` (`FamilyGraph.cs:32,37,48`) не покриті.
5. **`SpouseLink` в обхід `Create`** (object initializer із `Person1Id > Person2Id`).
6. **`ParentRole.Adoptive`/`Step`** — жоден тест не створює неблагонадійного зв'язку (B-17).
7. **Особа з 3+ батьками** — ні у валідаторі (B-18), ні в `ClassifySiblings`/`DetermineLineage`.
8. **Обидва батьки з `Gender.Unknown`** — гілка `KinshipCalculator.cs:301` не покрита.
9. **`Lineage.Mixed` для кузенів** (шлюб двоюрідних у попередньому поколінні).
10. **Свояцтво з `Gender.Unknown` сполучної особи для `SpouseSibling`** — гілка `UkrainianKinshipFormatter.cs:204` не виконується жодного разу.
11. **`AffinityKind.UncleAuntSpouse` в англійському форматері**; **детальний стиль для свояцтва** («шваґер (чоловік сестри)», `:211`).
12. **Пріоритет свояцтв:** «чинний, але далекий VS розірваний, але близький» (задокументовано в коментарі `KinshipCalculator.cs:195-199`).
13. **Глибокі прямі лінії:** `Pra(n)`/`Great(n)` тестуються лише до n=2; гілки `Ordinal` для `k ≥ 8` не покриті.
14. **`TreeMode.Ancestors` для особи з кількома шлюбами**; **шлюб усередині одного піддерева** (B-36); **`maxDepth` для `Ancestors`/`FullRelatives`** (там інша семантика — `Math.Abs(g) > depthLimit`); **порожній граф**.
15. **Демо-генератор:** дати не в майбутньому (B-02 — найдешевший спосіб закрити критичний баг); щонайбільше один активний `SpouseLink` на особу (B-31); межа `MaxPersons` на кількох сідах (B-33).

### Storage (4 файли, ~40 тестів — сильні на «битому JSON» і надійності запису)

1. **Помилки шляху ЗАПИСУ — не покрито взагалі.** Read-only файл, тека без прав, заповнений диск → правильний `MessageKey`. Саме тому B-09 і B-10 живі. (`File.SetAttributes(path, FileAttributes.ReadOnly)` відтворюється легко.)
2. **Скасування.** Скасування під час `WriteJsonAsync` не має псувати ціль, лишати `*.tmp`, скидати `IsDirty` чи зсувати `UpdatedAt`.
3. **Міграції.** Фейкової міграції 1→2 не існує: увесь блок `:289-302` ніколи не виконувався (B-28).
4. **Кодування з BOM.** Три кейси: валідний UTF-8 з BOM; BOM + невалідні байти (зараз впаде — B-03); UTF-16 BOM. Плюс: наш запис іде **без** BOM.
5a. **Проставлення версії при записі** (B-65) — тест `Save_stamps_current_app_version`. Наразі жоден тест
    не читає `Meta.AppVersion` узагалі, тому «1.0.0» і живе.
5. **Повний round-trip.** `Save_then_load_roundtrips_document` перевіряє 6 полів `Person` із 13. Не перевіряються `MaidenName`, `BirthPlace`, `PhotoPath`, `Notes`, `CreatedAt`/`UpdatedAt`, `ParentChildLink.Id`/`ParentRole`, `SpouseLink.Id`/`DivorceDate`, `Meta.CreatedAt`/`AppVersion`.
6. **Глобальні дефекти документа:** цикл A→B→A, троє біо-батьків однієї статі (B-15), `photoPath` з UNC/абсолютним шляхом (B-13).
7. **`IsDirty` під час збереження** (B-11) — легко пишеться через наявний гачок `FaultBeforePromote`, який може мутувати документ замість кидання винятку.
8. **`FamilyMerger` — лише 4 тести.** Не покрито: злиття, що **оновлює** поля наявної особи (B-04); колізія `Id` у різних людей; подвійний `Apply` (B-12); зв'язки, чиї особи не потрапили в `remap` (тихо зникають); дедуплікація подружжя у зворотному порядку Id; злиття, що створює цикл (B-14).
9. **Життєвий цикл:** `SaveAsync` після `Dispose`, `Dispose` під час збереження (B-45), паралельні `SaveAsync` + `LoadAsync`.
10. **Бекапи:** провал бекапу не валить збереження; legacy-імена не ламають ротацію (B-42); бекап не робиться, коли цілі ще немає.
11. **Гігієна:** `JsonFamilyStorage` реалізує `IDisposable`, але у **всіх** тестах створюється без `using` (`JsonFamilyStorageTests.cs:64,93,129,140`, `SaveDurabilityTests.cs:62,77,92…`, `CorruptFileTests.cs:45`) — на кожен тест витікає `SemaphoreSlim` і маскується клас помилок із B-45.

### App

Автоматизованих тестів немає взагалі. Мінімум, що варто покрити без WPF-хосту (ViewModels чисті):
`MainViewModel` — шляхи «Зберегти як» при помилці запису (B-08), `PromptSaveIfDirty` на всіх виходах (B-05),
кількість `Rebuild()` на одну дію (B-07, B-21); `SettingsService` — запис у недоступну теку (B-20).
